# MA Grafik — правила разработки

Эти правила обязательны для любых изменений в репозитории.

## Главный принцип

Не наращивать новый код поверх старой реализации без необходимости. Каждое изменение должно по возможности упрощать проект, а не создавать новый технический долг.

## Обязательная очистка в рамках каждого изменения

Если во время задачи обнаружен код, который после изменения стал старым, дублирующимся, временным или больше не используется, его нужно удалить в рамках того же изменения.

Перед удалением обязательно проверить, что новая реализация полностью заменяет старую и что удаление не ломает рабочую функциональность.

Удалять сразу:
- старые функции и обработчики, которые больше не вызываются;
- дублирующийся CSS и JS;
- временные и промежуточные файлы;
- закомментированный код, который больше не нужен;
- старые версии компонентов и реализаций;
- неиспользуемые переменные, импорты, зависимости и селекторы;
- устаревшие обходные решения, если их причина уже устранена;
- файлы `legacy`, `old`, `temp`, `backup`, если они действительно больше не участвуют в работе проекта.

## Запрещено

- Оставлять очевидный технический мусор «на потом».
- Создавать второй параллельный механизм, если существующий можно безопасно заменить.
- Дублировать одну и ту же бизнес-логику в нескольких местах без необходимости.
- Удалять код вслепую без проверки ссылок, вызовов и поведения приложения.
- Делать крупный рефакторинг только ради красоты, если он не нужен для текущей задачи.

## Порядок изменения

1. Найти существующую реализацию.
2. Определить, что именно заменяется.
3. Внести минимальное рабочее изменение.
4. Найти старый код, который новая реализация сделала ненужным.
5. Удалить этот код в том же изменении.
6. Проверить, что приложение работает после очистки.
7. Не оставлять временные файлы и временные обходные решения после завершения задачи.

## Особое правило для MA Grafik

`app.js` уже большой, поэтому новую независимую логику не следует без необходимости добавлять туда. По возможности использовать существующие тематические модули или аккуратно выносить новую самостоятельную логику в отдельный модуль, не ломая рабочую архитектуру.

При этом не выполнять большой рефакторинг всего приложения без отдельной необходимости: изменения должны быть постепенными, проверяемыми и безопасными.
