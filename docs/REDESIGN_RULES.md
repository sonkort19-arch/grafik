# MA График — правила безопасного редизайна

Эти правила обязательны для всех этапов редизайна MA График.
Цель: максимально точно повторить выбранный дизайн, не ломая рабочую логику приложения.

## Главный принцип

**Во время редизайна меняем внешний вид отдельно от бизнес-логики. Не улучшать и не переписывать то, о чём не просили в текущем этапе.**

## Обязательные правила

1. **Перед каждым этапом сохранять рабочую точку.**
   - Текущий production должен быть рабочим.
   - Перед новым этапом должен существовать понятный GitHub-коммит, к которому можно вернуться.

2. **Один этап = одна задача.**
   - Если переделывается экран «Сегодня», одновременно не менять CRM, расчёт графика, кошельки, авторизацию или другие модули.

3. **Дизайн отдельно от логики.**
   - При редизайне без отдельной необходимости не менять `schedule.js`, расчёт смен, Supabase-запросы, PIN, уведомления, финансовую математику и правила работы сотрудников.

4. **Не переписывать большие рабочие файлы целиком без необходимости.**
   - Особенно `app.js`.
   - Менять только нужные участки.
   - Большие рефакторинги — только отдельной задачей.

5. **Не менять порядок подключения скриптов без причины.**
   - Порядок загрузки `index.html` и `crm.html` считать критичным.
   - Любая смена порядка — только после отдельной проверки зависимостей.

6. **Не переименовывать рабочие `id`, классы и DOM-точки без проверки JavaScript.**
   - Перед переименованием проверить все обращения в JS.
   - После изменения проверить соответствующий сценарий в интерфейсе.

7. **Supabase и база данных — отдельный уровень риска.**
   - Редизайн не должен менять таблицы, RLS, Edge Functions, структуру данных или авторизацию.
   - Такие изменения делать отдельным этапом и отдельно тестировать.

8. **После каждого изменения запускать автоматические проверки.**
   - Проверка синтаксиса JS.
   - Существующие regression-тесты графика, ассистента и CRM.
   - Проверки Supabase Functions, если затрагивались соответствующие файлы.

9. **Сначала проверять Preview, потом Production, если изменение рискованное.**
   - Визуально и функционально проверить новую версию.
   - В production отправлять только рабочий вариант.

10. **Обязательно проверять телефон и компьютер.**
    - Минимум: iPhone/mobile и desktop.
    - Проверять меню, модальные окна, формы, клавиатуру, прокрутку и safe-area.

11. **После каждого этапа проверять критический сценарий MA График.**
    - Вход администратора.
    - Экран «Сегодня».
    - График на сегодня.
    - Открытие/закрытие смены.
    - Замена сотрудника.
    - История.
    - Обновление страницы.
    - Данные после обновления сохранились.

12. **Для CRM выполнять отдельную проверку.**
    - Открытие CRM.
    - Переключение «Все точки / Моба / Нова».
    - Открытие и создание заказа.
    - Клиенты.
    - Продажа.
    - Склад.
    - Финансы.
    - Не допускать повторения iPhone blank-screen регрессии.

13. **Не удалять старый CSS сразу.**
    - Сначала новый дизайн должен полностью заработать.
    - Удаление старых стилей делать отдельной финальной чисткой.
    - После чистки повторно прогонять тесты и визуальную проверку.

14. **Изменения PWA делать отдельно и осторожно.**
    - `manifest.webmanifest`, service worker, favicon и иконки не менять вместе с обычным редизайном без необходимости.
    - После PWA-изменений проверять обновление на телефоне.

15. **Если текущий этап не прошёл проверку — следующий не начинать.**
    - Исправить текущий этап или откатить его.
    - Не накладывать новые изменения поверх известной ошибки.

16. **Не менять рабочую бизнес-логику ради удобства дизайна.**
    - Дизайн должен адаптироваться к существующей логике, а не наоборот, если отдельное изменение логики не согласовано.

17. **Сохранять реальные данные и совместимость.**
    - Не сбрасывать localStorage/Supabase-данные пользователей.
    - Не менять ключи хранения и структуру данных без миграции и отдельного согласования.

18. **После каждого этапа фиксировать результат отдельным понятным коммитом.**
    - Один этап должен быть легко сравнить и легко откатить.

## Этапы редизайна

1. Сохранить и проверить текущую рабочую версию.
2. Разобрать выбранный дизайн и зафиксировать дизайн-систему.
3. Сделать новую общую оболочку: sidebar, topbar, mobile navigation.
4. Переделать экран владельца «Сегодня».
5. Переделать экран менеджера «Открыть смену / Закрыть смену».
6. Переделать основные модули: График, Календарь, История, KPI, Отчёт владельца.
7. Привести CRM к общему дизайну: Обзор, Заказы, Клиенты, Продажи, Склад, Финансы, Отчёты.
8. Переделать остальные разделы: Кошельки, Настройки, Помощник и системные окна.
9. Полная проверка, сравнение с выбранным макетом, пиксельная доводка и только затем очистка старого CSS.

## Условие перехода к следующему этапу

Следующий этап начинается только когда:
- текущий экран визуально принят;
- автоматические проверки прошли;
- критические пользовательские сценарии работают;
- mobile и desktop не имеют явных регрессий;
- production остаётся рабочим.
