# MA График — общий регламент безопасных обновлений

Этот документ действует для **всех** будущих изменений проекта: новых модулей, исправлений, редизайна, CRM, графика, смен, Supabase, кошельков, уведомлений, PWA, ассистента и любых других функций.

Цель: обновлять приложение постепенно, проверяемо и с возможностью быстрого отката, не ломая уже работающие функции.

## 1. Главное правило

**Одно обновление — одна понятная задача.**

Нельзя одновременно в одном изменении:
- переделывать дизайн;
- менять бизнес-логику;
- менять структуру базы;
- переписывать архитектуру;
- добавлять новый модуль;
- исправлять несвязанные ошибки.

Исключение — только если изменения технически неразделимы.

## 2. Перед любым изменением

Обязательно:
1. Проверить, что текущий `main` работает.
2. Зафиксировать текущий commit SHA как точку возврата.
3. Определить, какие именно файлы должны измениться.
4. Не трогать файлы, не относящиеся к задаче.
5. Для рискованного изменения сначала использовать Preview/отдельную проверку, а не сразу считать Production рабочим.

## 3. Рабочая версия всегда должна оставаться восстанавливаемой

- Каждый законченный этап должен иметь отдельный Git commit.
- Коммит должен описывать только выполненную задачу.
- Нельзя продолжать следующий этап, если текущий не прошёл проверки.
- Если после изменения появилась критическая ошибка, сначала исправить текущий этап или откатить его. Не накладывать сверху новые изменения в надежде, что они исправят проблему.

## 4. Дизайн не должен менять бизнес-логику

При UI/UX-изменениях запрещено без отдельной задачи менять:
- расчёт графика;
- правила смен;
- PIN и авторизацию;
- Supabase-запросы;
- финансовые расчёты;
- структуру данных;
- уведомления;
- права доступа;
- CRM-операции.

Если для нового дизайна нужно изменить JS, изменение должно быть минимальным и только для отображения/навигации.

## 5. Бизнес-логика не должна дублироваться

Для одной и той же сущности должен быть один основной источник расчёта.

Особенно:
- график сотрудников рассчитывается через центральную логику `schedule.js`;
- экран, уведомления и смены не должны иметь независимые копии правил графика;
- нельзя добавлять ещё одну реализацию уже существующего расчёта только ради нового экрана.

Если обнаружена дублирующая логика, её устранение выполняется отдельным контролируемым этапом.

## 6. Не переписывать большие рабочие файлы без необходимости

Особенно осторожно с:
- `app.js`;
- `styles.css`;
- `crm.js`;
- `index.html`;
- `crm.html`.

Правила:
- менять минимально необходимый участок;
- не переписывать весь файл ради небольшого изменения;
- новые большие функции по возможности выносить в отдельный модуль;
- разгружать `app.js` постепенно, а не одним большим рефакторингом.

## 7. Не менять порядок загрузки скриптов без отдельной проверки

Текущий порядок подключения модулей является частью архитектуры.

Для `index.html` и `crm.html` нельзя:
- переставлять `<script>` без необходимости;
- удалять существующий модуль без проверки зависимостей;
- подключать новый модуль в случайное место.

Изменение порядка скриптов считается рискованным изменением и требует отдельного smoke-теста запуска приложения, особенно на iPhone.

## 8. Нельзя переименовывать DOM ID и публичные классы вслепую

Перед изменением `id`, `data-*`, глобального имени или CSS-класса обязательно проверить все обращения к нему в JS/CSS/тестах.

Нельзя просто переименовать HTML-элемент ради красоты, если его ищет JavaScript.

## 9. Новый модуль должен быть изолирован

При добавлении нового модуля:
1. У модуля должна быть одна понятная ответственность.
2. Он не должен менять чужие данные напрямую без явного API/контракта.
3. Он не должен копировать уже существующую бизнес-логику.
4. Его стили не должны глобально ломать другие экраны.
5. Его ошибки не должны приводить к белому экрану всего приложения.
6. По возможности модуль должен fail-safe/fail-open: если второстепенный модуль не загрузился, основное приложение продолжает работать.
7. Для модуля нужно определить способ его отключения/отката.

## 10. CSS должен быть контролируемым

- Не добавлять бесконечно новые слои переопределений поверх старых.
- Новый дизайн сначала внедряется, проверяется, затем старые неиспользуемые правила удаляются отдельным этапом.
- Избегать слишком общих селекторов, способных затронуть чужие экраны.
- Для новых крупных модулей использовать собственный namespace классов.
- Проверять минимум desktop, iPhone и узкий экран.

## 11. Supabase и база данных — повышенный риск

Изменения Supabase выполнять отдельно от обычного UI-обновления.

Обязательно:
1. Не удалять таблицы/колонки/данные без отдельного подтверждения.
2. Миграции должны быть обратимо безопасными насколько возможно.
3. Новые поля сначала добавлять совместимо со старой версией клиента.
4. Не делать клиент зависимым от новой схемы раньше, чем схема доступна.
5. Проверять RLS/права доступа и Edge Functions.
6. Не помещать секретные ключи в frontend.
7. Publishable key не считать секретом, но не расширять его права.
8. Не менять существующие форматы данных без миграционного плана.

## 12. Изменения финансовой логики — отдельный этап

Для CRM-финансов и кошельков:
- UI можно менять отдельно;
- формулы, балансы, переводы, категории и расчёты нельзя менять вместе с дизайном;
- любые изменения математики должны иметь тестовые примеры "до → после";
- нельзя автоматически исправлять реальные финансовые данные без явного запроса.

## 13. Смены и график — критические функции

После изменения, которое может затронуть смены или график, обязательно проверить:
- кто должен работать сегодня;
- Моба/Нова;
- открытие смены;
- закрытие смены;
- время открытия/закрытия;
- PIN/устройство;
- однодневную замену;
- историю смен;
- обновление страницы;
- сохранность данных после перезапуска.

Однодневную замену не превращать в изменение базового цикла, если достаточно override.

## 14. CRM — обязательный smoke-тест

После изменений CRM проверить:
- запуск CRM без белого экрана;
- вход;
- переключатель `Все точки / Моба / Нова`;
- обзор;
- заказы;
- открытие карточки заказа;
- клиенты;
- продажи;
- склад;
- финансы;
- отчёты;
- создание/редактирование формы, если задача их затрагивает.

Особенно осторожно менять bootstrap и порядок CRM-скриптов.

## 15. iPhone проверяется обязательно

Проект используется как PWA/в браузере телефона, поэтому desktop-проверки недостаточно.

После UI-изменений проверить:
- ширину экрана;
- safe-area;
- нижнюю навигацию;
- модальные окна;
- клавиатуру;
- фокус input;
- отсутствие нежелательного zoom;
- вертикальную прокрутку;
- кнопки минимум удобного размера;
- отсутствие горизонтального выхода контента за экран.

## 16. PWA, иконки и Service Worker менять отдельно

При изменении PWA:
- проверить `manifest.webmanifest`;
- favicon;
- apple-touch-icon;
- service worker;
- cache version;
- обновление установленного приложения;
- отсутствие старого кэша, блокирующего новую версию.

Не смешивать изменение иконки/PWA с крупным функциональным обновлением без необходимости.

## 17. Автоматические тесты обязательны

Перед признанием изменения готовым должны пройти доступные проверки проекта:
- `node --check` для изменённых JS-файлов;
- regression tests;
- CRM regression tests, если затронута CRM;
- assistant tests, если затронут помощник;
- Deno/type-check для изменённых Supabase Functions;
- production/preview smoke checks по доступному workflow.

Если тест падает — этап не завершён.

## 18. После деплоя проверять не только статус READY

`READY` означает, что deployment собрался, но не гарантирует корректность интерфейса.

После деплоя нужно проверить:
1. Главная страница открывается.
2. Нет белого экрана.
3. Нет критических runtime errors.
4. Затронутый модуль реально открывается и выполняет основное действие.
5. На телефоне нет явного визуального регресса.

## 19. Ошибки должны быть локальными

Новый второстепенный модуль не должен падением останавливать всё приложение.

Где возможно:
- оборачивать необязательную инициализацию в безопасную обработку ошибок;
- показывать понятное состояние ошибки;
- сохранять доступ к основным функциям;
- логировать ошибку вместо полного падения приложения.

## 20. Сохранение данных важнее косметики

Любое изменение, затрагивающее сохранение:
- должно сохранять обратную совместимость;
- не должно очищать localStorage/облако без подтверждения;
- не должно менять ключи хранения без миграции;
- должно проверяться после refresh/restart;
- должно учитывать возможный offline/temporary network state.

## 21. Безопасность и доступ

Нельзя:
- выводить токены/секреты/PIN-хэши в интерфейс или логи;
- ослаблять авторизацию ради удобства;
- обходить проверки владельца/сотрудника;
- добавлять скрытые административные действия без явного контроля доступа.

## 22. Никаких "заодно улучшил"

Во время конкретной задачи запрещено добавлять несогласованные изменения вида:
- "заодно переделал архитектуру";
- "заодно изменил базу";
- "заодно поменял график";
- "заодно удалил старые функции";
- "заодно оптимизировал всё приложение".

Сначала завершить текущую задачу. Остальные улучшения оформить отдельным этапом.

## 23. Definition of Done — когда обновление считается готовым

Обновление готово только если:
- задача выполнена;
- изменены только нужные файлы;
- приложение запускается;
- тесты проходят;
- затронутая функция проверена вручную/smoke-тестом;
- данные не потерялись;
- iPhone/desktop проверены, если затронут UI;
- нет известных критических ошибок;
- есть commit для отката;
- результат на Production подтверждён после деплоя, если изменение выпускалось в Production.

## 24. Приоритет при конфликте требований

Если красивое решение повышает риск поломки, приоритет такой:

1. Сохранность данных.
2. Рабочая бизнес-логика.
3. Стабильность приложения.
4. Совместимость со старой версией.
5. Удобство.
6. Дизайн.

## 25. Как выполнять каждую будущую задачу

Стандартный цикл:

**Понять задачу → определить затронутые файлы → зафиксировать текущую версию → сделать минимальное изменение → проверить синтаксис/тесты → проверить функцию → проверить телефон/desktop при UI → задеплоить → проверить Production → только потом переходить к следующей задаче.**

`docs/REDESIGN_RULES.md` дополнительно действует для текущего редизайна. Если правила редизайна и этот документ пересекаются, применять более строгий безопасный вариант.
