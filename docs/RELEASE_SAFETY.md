# MA График — политика безопасных релизов

Этот документ дополняет `docs/PROJECT_RULES.md` и действует для любых обновлений проекта.

## Уровни риска

### Низкий риск
Примеры:
- текст;
- локальная правка CSS;
- подпись кнопки;
- документация;
- изменение, которое не затрагивает JS, данные, авторизацию, график, смены, финансы, CRM bootstrap или PWA.

Требования:
1. Отдельный commit.
2. Автоматические тесты должны пройти.
3. Проверить затронутый экран после деплоя.

### Средний риск
Примеры:
- новый UI-модуль;
- изменение JavaScript интерфейса;
- навигация;
- новые формы;
- изменение CRM-интерфейса;
- PWA/Service Worker;
- новый безопасный read-only вызов API.

Требования:
1. Отдельная ветка.
2. Pull Request в `main`.
3. GitHub Actions должны пройти полностью.
4. Проверить Vercel Preview.
5. Проверить desktop и iPhone для UI-задач.
6. Иметь понятный способ отката.
7. Только после этого объединять в `main`.

### Высокий риск
Примеры:
- Supabase schema/migration;
- RLS и авторизация;
- запись/удаление данных;
- график и правила смен;
- финансовая математика;
- порядок загрузки скриптов;
- bootstrap CRM;
- крупный рефакторинг;
- удаление старых полей/таблиц/ключей хранения;
- изменения, способные дать белый экран всему приложению.

Требования:
1. Отдельная ветка и PR обязательны.
2. Зафиксировать SHA рабочей production-версии до изменений.
3. Записать план отката до merge.
4. Для базы — проверить совместимость старого и нового клиента; перед разрушительными изменениями нужна резервная копия данных.
5. Все автоматические проверки должны пройти.
6. Preview/smoke-проверка обязательна.
7. Для затронутых критических функций провести ручной сценарий.
8. Merge только после подтверждения, что откат возможен.

## Стандартный путь любого обновления

`Рабочий main → ветка → изменение → тесты → Preview → ручная проверка → merge → Production smoke → следующий этап`

Не переходить к следующему этапу, пока предыдущий не подтверждён как рабочий.

## План отката

Для среднего и высокого риска перед merge нужно знать:
- SHA последней рабочей версии;
- какие файлы изменены;
- затрагивалась ли база;
- можно ли откатить только код;
- требуется ли обратная миграция данных.

Если production сломан:
1. Остановить следующие изменения.
2. Определить последний рабочий SHA.
3. Откатить текущий релиз или исправить только его причину.
4. Повторно прогнать тесты и smoke-проверку.
5. Не накладывать новые функции поверх аварийного исправления.

## Новые модули

Новый модуль должен:
- иметь собственную понятную ответственность;
- по возможности быть изолирован от существующих модулей;
- не копировать бизнес-логику графика, смен, финансов или CRM;
- не менять чужие данные скрыто;
- иметь локальные/namespace-стили;
- не приводить к падению всего приложения при собственной ошибке;
- иметь тест или stability-check для своей критической интеграции;
- быть добавлен в smoke/regression проверки, если он становится важной частью production.

## Что считается стоп-сигналом

Релиз не продолжается, если:
- упал хотя бы один обязательный тест;
- Preview даёт белый экран или runtime error;
- сломан iPhone layout у затронутого UI;
- изменились данные без предусмотренной миграции;
- нет понятного пути отката для высокого риска;
- изменение затронуло больше областей, чем было запланировано.

## Приоритет

`Данные → бизнес-логика → стабильность → совместимость → удобство → дизайн`.
